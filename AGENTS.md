# Project guidelines

- This is a personal open-source project. Do not change repository visibility, transfer it to an organization, publish releases or rewrite history without explicit owner authorization.
- Ordinary Jira reads/writes delegate to existing `acli`/`jira-cli` commands. The user explicitly approved the opt-in `--board <id>` Jira Software API bridge for exact Board/Backlog membership and confirmed single-ticket movement. It may reuse current acli Linux keyring credentials and read version-sensitive web-board metadata for actual manual issue-list membership/visibility, but OAuth login/refresh remains acli's responsibility. Never replace missing metadata with guessed statuses or the whole saved-filter scope. The user also explicitly approved authenticated read-only image attachment downloads/rendering. Only fetch numeric attachment IDs verified on the selected ticket through the CLI, using fixed Atlassian Cloud attachment-content endpoints with `redirect=false`; never fetch arbitrary/external media URLs, follow redirects, send credentials to CDN hosts, or log signed URLs. Bound HTTP/image decoding, cache privately per account, cancel stale requests, and keep attachment delete/upload unsupported. The user also approved read-only Jira field-metadata lookup (`GET /rest/api/3/field`) to identify numeric story-point fields by server names/schema rather than hardcoded IDs. Bound responses, pin account/site/origin, forbid redirects, retain CLI ordinary issue operations, and show unknown/ambiguous estimates instead of guessing. The user also approved read-only project-status metadata (`GET /rest/api/3/project/{project}/statuses`) at startup and refresh, including unused workflow states. Validate project keys, reuse the pinned metadata connection with bounded responses and no redirects, and retain cached suggestions on failure; statuses never determine Board/Backlog membership or override ticket-specific transition targets. Do not extend direct HTTP or credential access to other operations without explicit approval.
- The user explicitly approved a private local dotenv file containing their API token, company URL and settings. Keep real env files out of Git, require 0600 permissions, redact parser/auth errors, never place tokens in argv or export file values globally. The Board bridge may use this token; explicit CLI auth must pipe it to acli stdin. Ordinary Jira operations still use the CLI. Do not silently replace acli account/site; validate identity and require explicit `auth` when it differs.
- Use `tokio::process::Command` with argument arrays, never shell interpolation, for Jira operations.
- Never commit credentials, CLI account configuration, caches, ticket bodies, screenshots, or fixtures from real accounts. Tests use synthetic DEV tickets only.
- Never perform real Jira mutations as part of development/tests. Every user-facing write must target one validated ticket key and require explicit confirmation. Respect `--read-only` in both action entry and confirmation.
- Do not describe a status-grouped board or backlog JQL as an exact replica of a web board. Document unsupported CLI capabilities.
- Cache local ticket data only in account-scoped namespaces with private file permissions. Keep terminal control sequences out of untrusted Jira text and validate external URLs.
- Run `make check` and `make build` before committing. Keep backend, UI, and cache/config code separated.
